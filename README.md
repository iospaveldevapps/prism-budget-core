# BudgetCore

**Cross-platform mobile core in Rust, exposed to Swift via [UniFFI](https://mozilla.github.io/uniffi-rs/).**

BudgetCore is the platform-agnostic domain core of [PrismMoney (Budget Control Pro)](https://apps.apple.com/app/id6746616547), an iOS personal-finance app. It implements the *"auto-distribute the rest"* feature for envelope budgeting: given an amount of unallocated money and a set of envelopes with spending history, floors, caps, and priorities, it computes the optimal split using linear programming.

The business logic lives in a single Rust crate. Swift bindings are generated by UniFFI, the compiled static library ships as an `XCFramework`, and the whole thing is consumed by the app as a regular Swift Package — no Rust toolchain required on the consumer side.

> This repository also serves as the course project for the OTUS Rust course:
> *"Cross-Platform Mobile Core in Rust Using UniFFI"*.

## Why a Rust core?

| Concern | How this repo answers it |
|---|---|
| **Non-trivial math** | The allocation problem is a linear program (goal programming with priority weights). Rust's LP ecosystem (`good_lp` + the pure-Rust `microlp` solver) is mature, fast, and dependency-light — no C solver toolchains to cross-compile. |
| **Portability** | The crate has zero platform bindings inside. The same `suggest_allocation` can be exposed to Kotlin/Android, WASM, or a server binary; only the packaging layer changes. |
| **Safety across the FFI** | UniFFI generates the entire boundary — records, error enums, panic-safe call shims, memory management. There is no hand-written `unsafe` and no hand-maintained C header. |
| **Testability** | The solver is tested twice: pure Rust unit tests for the math, and Swift tests that exercise the *generated bindings* end-to-end, so binding regressions can't hide behind passing Rust tests. |

## Architecture

```
┌───────────────────────────────  iOS app (SwiftUI)  ──────────────────────────────┐
│  AutoAllocateSheet ──▶ BudgetAllocationEngine (Swift wrapper: SwiftData,         │
│                        currency conversion, presentation)                        │
└──────────────────────────────────────┬───────────────────────────────────────────┘
                                       │ import BudgetCore   (this Swift Package)
┌──────────────────────────────────────▼───────────────────────────────────────────┐
│  Sources/BudgetCore/budget_core.swift        ← generated by uniffi-bindgen       │
│  (EnvelopeInput, AllocationPlan, AllocationError, suggestAllocation)             │
├──────────────────────────────────────┬───────────────────────────────────────────┤
│  budget_coreFFI.xcframework          │ C ABI (RustBuffer serialization)          │
│  ios-arm64 / ios-arm64-simulator / macos-arm64 static libraries                  │
├──────────────────────────────────────▼───────────────────────────────────────────┤
│  src/lib.rs — Rust crate `budget_core`                                           │
│  goal-programming LP model, solved by good_lp + microlp (pure Rust)              │
└──────────────────────────────────────────────────────────────────────────────────┘
```

Design rules enforced at the boundary:

- **The core is pure.** It never touches persistence, currency conversion, or UI concerns — the Swift side converts everything to the base currency before calling in, and maps results back by `id` (never by array order).
- **Errors are typed.** `AllocationError` is a UniFFI error enum; Swift catches `NoEnvelopes`, `NegativeAvailable`, `InvalidBounds(id:)`, `Infeasible` as a real `Swift.Error` with localized descriptions.
- **Degradation is explicit.** When the requested floors don't fit into the available amount, the solver relaxes them proportionally and reports `minimums_were_relaxed = true` instead of silently pretending the plan is exact.

## The allocation model

`suggest_allocation(available, envelopes)` solves:

```
minimize    Σ priorityᵢ · dᵢ                     (priority-weighted deviation)
subject to  dᵢ ≥ xᵢ − targetᵢ                    (linearized |xᵢ − targetᵢ|)
            dᵢ ≥ targetᵢ − xᵢ
            minᵢ ≤ xᵢ ≤ maxᵢ                     (per-envelope floor/cap)
            Σ xᵢ ≤ available
```

where `targetᵢ` is the envelope's historical monthly average. The budget constraint is an inequality on purpose: once every envelope reaches its target, leftover money stays *reported as available* rather than being padded arbitrarily into some envelope.

## Swift API

```swift
import BudgetCore

let plan = try suggestAllocation(
    available: 1_000,
    envelopes: [
        EnvelopeInput(id: "groceries", historicalAverage: 400,
                      minAmount: 0, maxAmount: 600, priority: 1),
        EnvelopeInput(id: "transport", historicalAverage: 150,
                      minAmount: 0, maxAmount: 300, priority: 0.5)
    ]
)

for result in plan.results {
    print(result.id, result.suggestedAmount)
}
if plan.minimumsWereRelaxed {
    // Tell the user their floors couldn't be fully honored.
}
```

Everything above — the structs, the throwing function, the error enum — is generated from the Rust definitions in `src/lib.rs`. There is no hand-written glue.

## Building

Consumers never need any of this — the xcframework and bindings are committed. To change the Rust core:

```bash
# prerequisites (one-time)
rustup target add aarch64-apple-ios aarch64-apple-ios-sim aarch64-apple-darwin

make build        # rebuild xcframework + regenerate Swift bindings
make test         # cargo test + swift test
make lint         # clippy -D warnings + rustfmt check
```

The pipeline (`scripts/build-xcframework.sh`):

1. `cargo build --release` a `staticlib` for device, simulator, and macOS
   (the macOS slice exists so `swift test` runs natively on dev machines and CI);
2. `uniffi-bindgen generate --library` extracts FFI metadata from the built
   archive and emits `budget_core.swift`, the C header, and the modulemap —
   no `.udl` file to keep in sync, the Rust source *is* the interface
   (proc-macro mode);
3. `xcodebuild -create-xcframework` bundles the three slices;
4. the generated Swift file is copied into `Sources/BudgetCore/`.

CI runs this same pipeline and fails if the committed bindings drift from the crate (`reproducibility` job), so `src/lib.rs` and `Sources/BudgetCore` can never disagree on `main`.

## Using the package

In `Package.swift`:

```swift
.package(url: "git@github.com:iospaveldevapps/prism-budget-core.git", from: "0.1.0")
```

or in Xcode: *File → Add Package Dependencies…* with the same URL (the repo is private — SSH access or a GitHub token is required).

### Distribution note

The binary is committed in-repo (`binaryTarget(path:)`) rather than attached to GitHub Releases with a checksum (`binaryTarget(url:checksum:)`). For a private, single-consumer package this is the pragmatic choice: one artifact, one commit, no release automation, and SwiftPM still gets deterministic versions via git tags. If the package grows more consumers or the binary gets large, switching to checksummed release assets is a contained change to `Package.swift` plus a small publish step in CI.

## Versioning

Semantic versioning via git tags (`v0.1.0`, …). The FFI surface is the public API: adding a field to a UniFFI record or a case to an error enum is a **breaking change** for consumers and bumps accordingly.
